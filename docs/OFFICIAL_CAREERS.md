# 公司官网岗位采集

## 使用

运行原来的管理界面，在“公司官网岗位搜索”输入关键词（逗号分隔、任一命中）、岗位城市和公司入口，点击开始。内置目录包括南方数码、南方卫星导航及 NIQ；额外入口可自行填写。默认每公司最多8页、10条，路径深度最多3层，已有完整JD默认跳过。所有采集共享任务锁。停止按钮在当前页面操作完成后生效。

“浏览器动态页面”使用 Playwright 正常加载公开页面。“公开静态HTML”以校验证书的HTTP连接获取HTML，再用禁用网站脚本、阻止外部资源请求的Chromium提取；适合无需JavaScript的公开岗位，不能完成动态加载或登录。两种模式均不填写表单、不投递简历、不登录、不处理验证码。

命令：

```bash
python official_careers.py --keyword '数据分析,GIS,运营分析,analyst' --city 广州 --headless
python official_careers.py --sources official_sources.json --keyword 'analyst,research' --city 广州 --transport html --headless
```

## 发现和核实入口

公司目录由公开搜索结果建立，记录入口、公司和核验依据。程序读取入口里的招聘链接，沿同公司域名和直接链接的招聘系统租户继续访问；共享ATS不会扩展到其它公司。NIQ目录还包含搜索发现的一条广州岗位种子，只有访问官网并发现相同ATS租户后才会采用。

搜索引擎发现是可选的实验功能：每公司仅一次Bing关键词查询；先检查访问规则，禁止、未知或验证码时停止搜索。结果仅作为“未核实候选”展示，不自动认定为官网，不自动访问候选站点。这一功能尚未通过真实搜索引擎端到端验证，不能承诺任意关键词都能自动发现公司。现阶段稳定入口是公司目录或用户补充的招聘URL。

## 提取与保存

支持 JobPosting JSON-LD（含数组和@graph）、JobPosting Microdata，以及有明确标题和JD容器的详情页。无结构化数据、需登录、动态分栏或手风琴页面可能需要专用适配，不把整页、列表或搜索摘要当成完整JD。公司地址不会充当岗位地点；城市未知时不计入城市筛选。广州同时匹配Guangzhou/Canton。

岗位按URL去重；保留原始JD、行业原文、地点原文、币种、招聘入口、发现来源、核验状态、发布日期及截止时间。非人民币薪资不加入人民币月薪筛选。已过截止时间的记录不加入新采集结果；没有截止时间的公开页面标为“页面可访问，是否在招待核实”，不宣称仍有效。

现有的CSV、JSON和分类ZIP导出可继续使用，新增来源与时效字段可回导。

## 访问边界

原招聘平台规则门禁保持不变。仅在新官网模式中，robots.txt明确返回404被识别为“未发布robots文件”，与未知规则、403、429或验证页区分；这不代表获得网站全部用途授权。禁止路径仍停止。沿用单任务锁、动作间隔、预算和拒绝冷却；不改变IP/账号或隐藏浏览器身份。

静态模式不运行网站脚本，浏览器模式只允许GET/HEAD请求。这会使依赖POST查询的动态招聘网站无法完整工作，留待具体验证后适配。

## 云端验证（2026-10-22）

- Playwright 1.51.0，Chromium 134，Python 3.12；按requirements安装pypdf后原有测试通过。
- 云端Chromium直接联网遇到当前环境代理的证书信任错误，未关闭证书校验。浏览器直连外站端到端验证未完成。
- 实际使用校验证书的HTTP获取SmartRecruiters两个公开页面，并在Chromium静态模式提取。两页均得到Microdata JD，地点明确为Guangzhou；NIQ的Research Manager, Qualitative提取3721字符，路易达孚Industrial Analyst提取3598字符（长度是本次结果，不作为固定测试断言）。
- NIQ官网招聘目录已观察到指向自身SmartRecruiters租户的链接。路易达孚样本来自搜索发现的招聘系统页面，官网关联尚待核实。
- 两条样本的发布日期分别为2026-09-11、2026-07-31；缺少明确截止时间，均标记在招状态待核实。经理岗位含5年以上经验要求，采集成功不代表适合应届求职。
- 同样任务再次执行：两条均命中缓存，未重新请求JD。运行数据位于data目录，不提交招聘正文或本地数据库。
- 另有离线Chromium测试：JSON-LD嵌套、Microdata多标题页面、拒绝整页冒充JD，以及URL边界、城市匹配、截止时间、404与拒绝区分测试。

## 单任务100条批量验收（2026-10-22）

新增`feed_collect.py`及`public_feeds.py`，按[Lever官方公开Postings API文档](https://github.com/lever/postings-api)读取雇主岗位列表；只调用文档中的公开GET，不涉及投递接口和密钥。分页每页最多200条，每来源最多5页，全部雇主共享接口域名的间隔/每日预算/冷却状态。API数据本身携带JD正文、要求列表及补充说明，不需要逐岗打开100次网页。

管理界面新增“官网公开岗位批量采集与验收”，目标默认100条。默认筛选仍为广州及相关关键词；如果匹配不足会显示`incomplete`，不会用其它城市补齐。已有完整JD默认不再计入新增任务；可明确勾选刷新。旧的网页采集仍独立保留其页面预算。

本次容量命令（明确不限地区/岗位类型）：

```bash
python feed_collect.py --target 100 --city '' --keyword ''
```

同一任务读取4个公开雇主列表，检查264条原始记录，去重、排除人才库/内容不足等记录后，实际新增100条、更新0条、跳过写入0条。来源包括Ninja Van 79条、Coates Group 15条、Pattern 6条；文远知行列表也参与读取，但本次优先排序后的100条未选入其岗位。单任务约52.66秒，4次列表接口请求；100条各有独立来源URL、发布ID、JD和正文SHA256，已从SQLite读回复核100个摘要全部一致。

其中地点明确包含广州的11条，广州且命中“数据分析/GIS/运营分析/analyst”的1条。因此仅100条批量容量验收通过，100条广州目标岗位验收尚未通过。GIS已改为英文短词边界匹配，防止把logistics误算成GIS。

逐条元数据及核验清单见`docs/BATCH_ACCEPTANCE_100.json`。这是实际接口采集，未使用Mock岗位；单元测试另外使用合成数据并与验收分开。完整JD及任务日志位于`data/runs/<task_id>/`，不纳入Git。公开列表存在不等于公司保证仍在招，投递前仍需核实。
